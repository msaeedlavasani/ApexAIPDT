# DPT Credit Economy

**Status:** Concept / v0.1 — documented for future implementation

## Purpose

DPT uses a contribution-aware credit model to create a two-way value exchange between projects and the DPT ecosystem.

The basic principle is:

> Consume reusable value → spend credits.  
> Create reusable value → earn credits.

Credits are intended to reward **accepted reusable value**, not raw activity.

## Contribution Lifecycle

Every contribution starts as a candidate and must pass DPT validation before its reward becomes spendable.

```text
Contribution Created
        ↓
     CANDIDATE
        ↓
   DPT Validation
        ↓
 ┌──────┴──────┐
 ▼             ▼
ACCEPTED     REJECTED
  ↓
Reward          0 Credits
  ↓
Credited
```

Recommended statuses:

- `CANDIDATE` — submitted and waiting for review.
- `UNDER_REVIEW` — validation is in progress.
- `ACCEPTED` — contribution is accepted into the relevant Pool.
- `REJECTED` — contribution did not meet acceptance criteria.
- `DUPLICATE` — equivalent knowledge or asset already exists.
- `DEPRECATED` — previously accepted but no longer recommended.

## Pending Rewards

The UI should distinguish earned-but-unconfirmed rewards from spendable balance.

Example:

> **Register a valid Pitfall**  
> Reward: **+3 Credits**  
> Status: **CANDIDATE**  
> *As soon as the contribution is approved, 3 Credits will be added to your balance.*

A useful account model is:

```text
Balance: 120 Credits
Pending: +9 Credits
```

After acceptance:

```text
Candidate
   ↓
Accepted
   ↓
Pending Reward +3
   ↓
Balance +3
```

## Example Rewards

Initial examples only; these values must remain configurable and must not be hard-coded into the architecture.

| Contribution | Example reward |
|---|---:|
| Validated Pitfall | +3 Credits |
| Validated Component | +3 Credits |
| Validated Module | +3 Credits |
| Validated Skill | +3 Credits |
| Validated Agent | +3 Credits |
| Accepted reusable improvement | +3 or more Credits |
| High-value reusable fix | Variable |

A contribution may receive **0 Credits** when it is duplicated, low quality, purely project-specific, or otherwise fails the acceptance criteria.

## Consumption

Projects spend Credits when consuming DPT reusable value. Initial examples:

| Action | Example cost |
|---|---:|
| Fetch Component | 10 Credits |
| Fetch Module | 15 Credits |
| Fetch Skill | 10 Credits |
| Fetch Agent | 20 Credits |

These are illustrative values only and must remain configurable.

## Credit Sources

Credits may eventually come from two sources:

1. **Earned Credits** — generated by accepted contributions.
2. **Purchased Credits** — included in a subscription or purchased usage allocation.

The contribution system and the billing system should remain separate so pricing can evolve without changing the contribution lifecycle.

## Quality Principle

> **Credits reward accepted reusable value, not activity.**

DPT must not incentivize projects or agents to flood Pools with meaningless assets. Validation, deduplication, quality assessment, and reusability checks are therefore prerequisites for rewarding contributions.

## Credits vs Reputation

Credits should not be treated as the same thing as reputation.

A project may have many Credits because it contributes frequently, while another may have fewer Credits but a stronger contribution-quality or reliability reputation.

Potential future dimensions include:

- Credit balance
- Pending Credits
- Contribution score
- Contribution quality score
- Reliability score
- Network reputation

## Future Considerations

This document intentionally does **not** finalize pricing, exchange rates, subscription tiers, or the exact credit economy. Those decisions should be made later using real usage, infrastructure cost, contribution quality, and ecosystem data.

The important architectural decision for now is the lifecycle:

```text
Consume value → spend Credits
Create reusable value → submit contribution
Validate → accept/reject
Accept → reward Credits
```
